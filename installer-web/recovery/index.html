Recovery and unbrick guide

For ESP32-based CYD boards that fail to boot after flashing. Read this guide before using any installer. A failed firmware flash usually does not destroy the ESP32 ROM download mode, but recovery is not guaranteed.

Stop before erasing

Do not use erase_flash, overwrite bootloader or partitions, or flash an image from another board until you have identified the exact chip, flash size, board variant and verified recovery images. An erase can permanently remove unique settings, API keys and factory firmware when no backup exists.

1. Identify the symptom

  1. Power off the board. Check USB cable, power source and obvious physical damage.
  2. If the display is blank, check whether a serial port appears on Windows Device Manager. A blank screen alone does not prove a brick.
  3. Disconnect any other app holding the serial port (PlatformIO monitor, browser tabs, other flashers).
  4. Record any serial boot messages at 115200 baud, if available. Never post credentials or full flash dumps.

2. Check ROM download mode (non-destructive)

  1. Use a data-capable USB cable and a supported serial driver for your USB bridge.
  2. If automatic reset fails, hold the board's BOOT button (or the verified GPIO0-to-GND boot method for your exact board), tap RESET, then release BOOT. Do not short unknown pins.
  3. Install Python and the project's documented esptool version. In a terminal, run python -m esptool --port COM5 chip_id, replacing COM5 with your port.
  4. If the chip responds, the ROM loader is accessible. This is encouraging, but does not verify the flash contents or board compatibility.

3. Preserve evidence before attempting a repair

  1. Save the original backup image and accompanying checksum/metadata in a private directory. Never upload it to GitHub or support tickets.
  2. If no backup exists, avoid additional writes until the chip and partition layout are confirmed. Reading flash may still be possible.
  3. Confirm whether flash encryption or secure boot is enabled; either may prevent ordinary backup or restoration.

4. Choose a recovery path

  1. Device still boots: use only a validated in-app update method for that exact firmware and partition layout.
  2. ROM loader responds, device does not boot: restore only a verified image for the same hardware with validated offsets. A full backup must match the original flash capacity and target; do not blindly write an unknown image.
  3. ROM loader cannot be reached: try another data cable, USB port, driver and verified BOOT/RESET sequence. Hardware troubleshooting may be required.

There is intentionally no generic write command here. Bootloader offsets, partition table location, OTA state and flash encryption must be checked for each release and board.

5. After recovery

  1. Confirm the device boots repeatedly and the touchscreen functions.
  2. Check Wi-Fi and channel settings without exposing secrets.
  3. Rotate credentials if a backup or diagnostic log was shared accidentally.
  4. Keep the recovery image offline and record the board revision and firmware version.

Current installer status

Browser application-only flashing and subsequent boot have been tested on one supported CYD. Full three-image installation, browser-native backup, full-device restore and recovery from a failed flash have not been hardware validated. The browser installer can write firmware; proceed only after reviewing the risks. Open read-only USB diagnostics.
